Installing the add-ons

You do not need to reinstall MATLAB if you missed them the first time.

  1. Open MATLAB.
  2. Home tab → Add-Ons → Get Add-Ons.
  3. Search Image Processing Toolbox → Install.
  4. Search Statistics and Machine Learning Toolbox → Install.

Then check they are really there. Type this at the >> prompt:

ver

You must see both of these in the list:

Image Processing Toolbox                 Version ...
Statistics and Machine Learning Toolbox  Version ...
If either is missing, nothing below will work. Image Processing reads the TIFF stacks and does the mask and density work; Statistics does the diffusion fitting and the Monte-Carlo null behind contact-site detection.

Set up · How your data must be laid out

This is where most first attempts fail. Five minutes here saves an afternoon.

The three folders you make

One folder per experiment. Inside it, exactly three sub-folders — you make these; the tools make the rest.

MyExperiment/          ← "the project folder". Point the tools at THIS.
├── spt/               ← your single-particle movies   (you)
├── er_seg/            ← ER segmentation masks         (you)
├── mito_seg/          ← mitochondria masks            (you)
├── tracks/            ← Tool 1 writes this
└── analysis/          ← Tools 2 and 3 write this
Spell them exactly spt, er_seg, mito_seg — lower case, with the underscore. This one bites people: Tool 1 also accepts erseg and mitoseg without the underscore, but Tools 2 and 3 do not. Name them the short way and Tool 1 looks like it worked, then Tool 3 quietly finds no masks and you get no contact sites, with no error.

The naming rule

Each cell is three files that share a stem and differ only in the ending. The shared part is the cell key, and matching is done on it.

ExampleEnding
movie250408_WT_012_C3.tif_C3 — your channel token, anything
ER mask250408_WT_012_er.tiff_er
mito mask250408_WT_012_mito.tiff_mito

Any of these endings work:

  • movie — _spt, _spt1, _spt2…, or your own token like _C3, _VAPB
  • ER — _er, _er_mip, _2_TA_BC
  • mito — _mito, _mito_mip, _ch1_mito, _3_TA_BC
If your movies carry a channel token, the tools work it out themselves by comparing movie names against mask names. Leave Tool 1's Strip regex box empty and the Scan line tells you which token it found and why.

ilastik users: exports ending _Probabilities, _Simple Segmentation, _Segmentation, _Uncertainty or _Object Predictions are stripped automatically — no renaming needed.

If you do not have both channels

You do not need both. Declare what the project has in a channels.json at the project root:

{ "channels": [ { "key": "er", "role": "support" } ] }

With no such file you get the standard ER + mito setup, which is what you want in almost every case. See Transparency & provenance for what the roles mean.

Set up · Running the three tools

Tell MATLAB where the code is

Once per MATLAB session, with your own path:

addpath('/Users/yourname/Documents/SPTinMatlab')

Nothing visible happens. That is correct.

To stop retyping it: Home → Set Path → Add Folder…, pick the SPTinMatlab folder, then Save. Now it is remembered and you can skip this step forever.

Then, in order

run_track      % Tool 1 — detect and track
run_curate     % Tool 2 — review, then build
run_analyze    % Tool 3 — contact sites and dwell

Each tool reads what the previous one wrote, so the order matters. Full walkthroughs are in Tool 1, Tool 2 and Tool 3; the short version:

  1. Tool 1 · Match files — pick the project folder (the one containing spt/, not spt/ itself), press Scan, and read the result line. Green with a cell count and a token is good; amber means your naming does not pair up — go back to the naming rule above. Then Detect → Track → filter → Export.
  2. Tool 2 · Import & Curate — cells load themselves from tracks/; there is no file picker. Review, then Export curated (or Export + Next ▶). On Build & QC type a Name and press ▶ Build + QC. This is the slow step, done once.
  3. Tool 3 — set the project folder, then Contact sites → Refine → Sites → Dwell.

Quick start

  1. Track (run_track): point the three folder pickers at spt/, er_seg/, mito_seg/ → Scan. On the Detect tab set the top-percentile (default 6 %); on the Track & filter tab set link/gap distances and pick a Linking mode from the dropdown (Euclidean · ER-penalty · ER-geodesic); run, filter (min length 50), export.
  2. Curate & Build (run_curate): import the curated tracks, type a Name for this build, then ▶ Build + QC (this is the slow MSD step — done once). QC individual tracks.
  3. Analyze (run_analyze): set the project folder — it opens the active build; on Contact sites pick a cell → Detect all → Save; on Refine tidy the boundaries; on Sites run the mapper; on Dwell compute residence times.

Tool 1 · Track & filter

Launch with run_track (which adds tool1_track/ to the path and calls spt_app). One window titled SPT Track — match · detect · track · filter · export, four tabs: 1 · Experiment, 2 · Match files, 3 · Detect, 4 · Track & filter. It opens on Match files, because that is where a fresh session starts.

spt/ · er_seg/ · mito_seg/→ Match files→ Detect→ Track & filter→ tracks/<base>_tracks_filtered.xml + _spots_filtered.csv

Nothing in this tool is called "curation": Tool 1 only filters tracks, by length and net displacement. Density / step-variance curation and per-track inspection are Tool 2's job.

The top bar — calibration, map units, help

Five controls sit above the tabs and apply to every tab. The two calibration numbers are used by everything downstream (DoG scale, link radius in pixels, µm coordinates in the CSV, T_s), so set them before you tune anything.

ControlDefaultWhat it does

Frame interval (s)0.020064Seconds per frame. Limits 1e-6 … 100. Only used to write T_s in the CSV and frameInterval in the XML — it does not affect detection or linking.
Auto—Reads the calibration out of the current cell's TIFF with spt_tiff_calib and fills three things: pixel size, frame interval, and the display range.

It understands ImageJ/Fiji files. Fiji stores the scale in XResolution and the unit in a plain-text block in ImageDescription, setting ResolutionUnit to None because microns are not one of TIFF's two units (inch/cm). The old reader looked only at the resolution tags and gave up on None — so the one case that mattered most was the one it rejected. A real block looks like:

ImageJ=1.54f
frames=5703
unit=micron
finterval=0.010519135743379593
min=131.0
max=1904.0

XResolution is then pixels per unit, so 6.25 with unit=micron is 1/6.25 = 0.16 µm/px. finterval is the frame interval in seconds (fps is used only when finterval is absent or zero — a stack with no time calibration carries finterval=0, which must never become dt=0). min/max is the display range Fiji was showing when the file was saved.

Files with genuine Inch/Centimeter resolution tags still work as before. Anything not actually readable comes back unset rather than guessed — a wrong pixel size silently rescales every distance, area and diffusion coefficient downstream, so nothing is far safer than something plausible. Accepted ranges: 0.005 … 5 µm/px and 1e-6 … 3600 s. unit=pixel means uncalibrated and is refused; so is unit=m at a scale that would imply a 160 mm pixel.

The status line reports exactly what was read and what was not, e.g. "Read from the TIFF: 0.16 µm/px · 0.010519 s/frame (95.06 Hz) · display 131–1904 (as saved in Fiji)".

Map axesµmUnits for the kept-vs-removed track map on the Track & filter tab only (µm or px). Pixels are recovered as x_px = X_um/pixel + 1.

How the channel tokens are bridged (spt_match)

Matching is by a derived cell key, not by position in the folder. spt_match builds the key from a filename by stripping, in this order:

  1. the extension — \.(tif|tiff|h5|hdf5)$;
  2. an ilastik export token at the end of the name — Probabilities, Simple Segmentation, Simple_Segmentation, Segmentation, Uncertainty, Object Predictions, Object_Predictions (preceded by a space or underscore);
  3. your Strip regex (default _VAPB), applied anywhere in the name;
  4. the per-channel suffix, anchored at the end of the name:
    ChannelSuffix pattern
    SPT_spt\d*
    ER_(2_TA_BC|er_mip|er)
    mito_(3_TA_BC|mito_mip|ch1_mito|mito)

Every step is case-insensitive. Worked example, straight from the function's own header:

spt : 250408_WT_012_spt1.tif           -> strip .tif, strip _spt1        -> 250408_WT_012
ER  : 250408_VAPB_WT_012_2_TA_BC.tif   -> strip .tif, strip _VAPB,
                                          strip _2_TA_BC                 -> 250408_WT_012   ✓ match

The ER and mito folders are turned into key → path maps and first match wins (a duplicate key later in the folder is ignored). A cell's erSeg/mitoSeg is '' when no file matched. The key is what the app shows everywhere as the cell name; the output filenames use the SPT stack's own basename, which is not the same string — for the example above the key is 250408_WT_012 but the outputs are 250408_WT_012_spt1_spots.csv and friends.

If a segmentation does not match, you get no error — just a ✗ in the table and a silently ER-unaware run for that cell. Read the summary line under the pickers ("12 cell(s): SPT 12, ER-seg 12/12, mito-seg 9/12.") before you run a batch. The usual fix is the Strip regex: compare one SPT name against one seg name and strip whatever only one of them carries.

Auto runs ImageJ's own algorithm, not a percentile stretch. ImageJ builds a 256-bin histogram and walks in from each end until it finds a bin holding more than pixelCount/5000 pixels. That count-based rule is the point: on a single-molecule frame — almost all dark background — a 99.8th-percentile white point still sits inside the noise and every real spot saturates, whereas the count rule steps over the sparse bright tail and leaves the spots intact. Clicking Auto again halves the threshold and stretches further, exactly as ImageJ does.

It is computed over a sample of the whole stack, not the current frame, so the brightness does not change as you scrub a several-thousand-frame movie. That is the other half of "looks like Fiji": Fiji holds one range for the stack.

Right-click Auto for Reset to full stack min–max — Fiji's Reset. When the file carries Fiji's own saved range (min/max in its ImageJ block) that exact range is used, both here and when the cell first opens.

What the DoG actually computes

Detection is a band-pass blob finder, not a Gaussian fit. spt_dog does two things to each frame:

rpx   = (diameter_um / pixel_um) / 2          % this spot's RADIUS in px
scale = rpx / 2.3181                          % 1.0 at 0.5 µm and 0.10785 µm/px
sBg = 6.0*scale;  s1 = 1.0*scale;  s2 = 2.2*scale

hp  = frame - gblur(frame, sBg)               % background high-pass
dog = gblur(hp, s1) - gblur(hp, s2)           % band-pass at the spot scale

The wide blur removes uneven background; the difference of the two narrow blurs suppresses single-pixel shot noise while keeping structures the size of a spot. All three sigmas scale with the spot's pixel radius, so the filter follows your diameter and your camera; at the reference (0.5 µm at 0.10785 µm/px, radius ≈ 2.32 px) they are exactly the ERAware values 6 / 1.0 / 2.2 px. Blurring uses symmetric padding and a 2·ceil(4σ)+1 kernel to match scipy, so detections match the Python original at the default.

spt_detect then, on the dog image:

  1. Thresholds — either the absolute value handed in, or (if none) a per-frame fallback median + 4·MAD, where MAD = 1.4826·median|dog − median|. The status line prints thr MAD when that fallback is in force.
  2. Finds 5×5 local maxima above threshold (dog ≥ imdilate(dog, ones(5,5))), and drops any peak within 2 px of the border.
  3. Non-max suppresses in descending quality: accept the strongest first, then reject any candidate within 2 px (Chebyshev) of an accepted one. So detected spots are always > 2 px apart.
  4. Refines to sub-pixel with a 5×5 intensity-weighted centroid on the high-pass image (negatives clipped to zero). There is no fitted PSF width, hence no per-spot Cramér–Rao precision — use Tool 2's MSD-intercept σ_loc instead.

Each spot's quality is the DoG value at its integer peak. That is the number on the histogram's x-axis, the number in the QUALITY column, and the number both threshold modes cut on.

Separately, spt_measure reports MEAN, MAX and TOTAL intensity over a disk of radius (diameter/pixel)/2 px (≈ 2.32 px at the defaults) on the raw, non-background-subtracted frame. Border spots use a partial disk — out-of-frame offsets are dropped, not clamped, so edge spots are not inflated.

The two threshold modes, and the pooled percentile

Top % — adapts to each cell.

spt_pool_quality takes 40 frames spread evenly through the movie, runs the same DoG on each, and collects the DoG values of every 5×5 local maximum that clears a light per-frame floor of median + 2·MAD. (Note the two different ks: 2 for "is this a plausible candidate worth pooling", 4 for the per-frame fallback threshold when nothing else is set.) The result is the movie-level quality distribution q — the histogram you see. The threshold is then simply

thr = prctile(q, 100 - Top%)          % Top% = 6  ->  the 94th percentile of q

and that one absolute number is applied to every frame of the movie. This is the point of pooling: the cut is set from the movie as a whole rather than re-derived frame by frame, so it does not drift with a bright or dim frame, yet it still adapts to each cell's own signal level.

Quality ≥ — the same cut for every cell.

A fixed absolute DoG-quality gate, in histogram units, applied unchanged to every cell. Use it when you need detection to be directly comparable across cells — Top % deliberately is not, since 6 % of a bright cell and 6 % of a dim one are different absolute cuts. Switching the dropdown to Quality ≥ while the spinner is still 0 seeds it from the current percentile threshold (rounded to 3 decimals), so you start from a value you have already seen work, then adjust. Leaving it at 0 means "unset", which falls through to the per-frame median + 4·MAD fallback — almost certainly not what you want.

The resolved threshold is stored per cell. Previewing a cell writes its diameter, Top %, threshold mode, Quality ≥ value and the resolved absolute threshold onto that cell. At run time:
  • a cell you previewed is tracked with exactly the absolute number the preview showed — the pooled percentile is not recomputed, so what you saw is what you get;
  • a cell you never opened in Detect inherits the Detect tab's current policy. In Quality ≥ mode that means your fixed gate really does apply to every ticked cell, not just the one on screen. In Top % mode it pools that cell's own 40 frames at run time and takes its own percentile.
The Run buttons' tooltip mentions a fall-back of "Top 10%"; that is the engine's default when the field is absent altogether — Scan sets 6 on every matched cell, so in practice an un-previewed cell runs at Top 6 %. Either way the policy is written into <base>_settings.txt and detection_summary.csv — but the resolved absolute number is recorded only for a cell you previewed. An un-previewed Top % cell has its percentile resolved inside spt_process_cell, which never hands the value back, so detection.thr_abs reads the literal (pooled top-percentile) and thr_abs in detection_summary.csv reads NA. You get detection.top_percent and the diameter instead — enough to reproduce the cut, but not the cut itself. The same gap applies to an un-previewed cell left at Quality ≥ 0, where the per-frame median + 4·MAD fallback goes unrecorded and quality_min prints (n/a). If you want the absolute number on record, open the cell in Detect once before running it.

The elongation / motion-blur readout

Because localization is a centroid and not a fit, there is no fitted width to flag a bad spot with. Instead spt_detect's second output measures the intensity second-moment shape of each spot on a 7×7 window about the sub-pixel centre (the centroid window stays 5×5, for parity with the original):

M = [Mxx Mxy; Mxy Myy]        % intensity-weighted second moments about the centroid
eig(M) -> sigMaj ≥ sigMin      % principal-axis widths, px
ELONGATION = sigMaj / sigMin   % 1.0 = round
ORIENT_DEG = major-axis angle, 0–180°

A stationary spot is round (elong ≈ 1). A particle that moves during the exposure smears into a streak along its direction of travel, so elong rises and ORIENT_DEG points along the motion. The app's blur flag is elong ≥ 1.5 (a single constant, ELONG_BLUR): it colours the preview rings red and drives the N likely motion-blur (elong≥1.5, med E) part of the status line, where med E is the median elongation over all spots in this frame.

This is a diagnostic, not a filter. Nothing in Tool 1 removes elongated spots. Both columns are written to the CSV (ELONGATION, ORIENT_DEG) so you can act on them later. Read the median: if it sits near 1.1–1.2 your exposure is short enough for these dynamics; if half your spots are streaked, the frame interval is too long for the fast population and the localizations at those points are smeared, not precise.

The linker is TrackMate-style LAP. Each frame pair is solved as a linear assignment (matchpairs) against a cost of leaving a spot unlinked

d0 = R·(1 + λ) + 1          % px;  ≈ 30.7 px at link 0.8 µm, λ = 3

which sits above any feasible link cost, so a partner within range always beats a birth/death. Chains are then assembled by walking forward from every spot with no incoming link, chains shorter than 2 spots are discarded, and finally gap closing runs: for each track end, in order of end frame, look at gaps of 2, 3, … maxGap+1 frames and take the nearest unused start within G, stopping at the smallest gap that yields a candidate. Each start can be consumed once.

The three linking modes, in depth

1 · Euclidean — 'euclid'. Distance only. Cost = ‖p − q‖ in pixels, Inf beyond R. The ER masks are ignored entirely, gap closing applies no ER test, and λ is irrelevant. This is the baseline: use it when you have no ER segmentation, or when you want tracking that makes no assumption about where the protein may travel.
2 · ER-penalty — 'penalty', the default. A soft bias, not a gate: 
off  = fraction of the p→q straight segment's MIDDLE (20–80%) lying OFF the ER mask
cost = ‖p − q‖ · (1 + λ · off)

The endpoints are excluded from the sample deliberately — the endpoints are the two spots, so including them would measure the spots' own ER-ness rather than the question being asked, which is does the path between them cut across a gap in the ER? With λ = 3:

Path vs ERoffMultiplier
entirely on ER0×1.0 — no penalty
half off ER0.5×2.5
entirely off ER1.0×4.0

Because the assignment only compares costs, an off-ER partner still wins if it is enough closer: at λ = 3 a fully-off-ER jump must be about 4× shorter than a fully-on-ER alternative. And since d0 = R(1+λ)+1 sits just above the worst penalized in-range cost, even a fully-off-ER link still beats leaving the spot unlinked. Nothing is ever refused, and no detection is ever excluded — that is the point: VAPB does transiently leave the ER, and this mode keeps those excursions while still preferring the ER-respecting interpretation when the two are comparable.

Gap closing keeps the matching soft rule: reject a bridge whose straight segment is more than 50 % off the ER, evaluated on the end frame's mask. A veto, not a requirement — up to half the bridge may be off-ER.

The mask this mode is measured against is the per-frame ER dilated by a diamond of radius 2 (up to 2 px, in spt_process_cell), which is more generous than the strict mode's slack. And note the fail-open asymmetry: if a frame's ER mask is missing — no page for that frame in the ER stack — the penalty simply is not applied there (plain Euclidean cost), and the gap-close veto is skipped. A mask that is present but all-false is a different case, and the two skips do not cover it: off is then 1 for every candidate, so every in-range cost is multiplied by 1+λ — uniformly, so the assignment itself is unchanged — but the gap-close veto rejects every bridge ending on that frame. Soft mode never refuses a frame-to-frame link for want of a mask; it can still refuse a gap close.

3 · ER-geodesic — 'geodesic'. A hard constraint, and it works in two stages.

Stage 1 — the detections are pre-filtered, before the assignment. For every frame, each detection is tested against its own frame's ER support, and one that is not on it is removed from the detection list outright. Doing this before the LAP is what makes the guarantee hold by construction: an off-ER detection is then unavailable to frame-to-frame linking, to chain assembly, and to gap closing. There is no route by which it can end up in a track.

Stage 2 — surviving links are costed along the ER. A link p (frame t) → q (frame t+1) is allowed only if all three hold:

  1. p sits on frame t's ER support;
  2. q sits on frame t+1's ER support — its own frame, because the ER moves between frames;
  3. q is reachable from p along frame t's ER within R (bwdistgeodesic, quasi-Euclidean, on a local crop of radius ceil(R)+2 px).

The cost is then the along-ER path length, so a link that must detour around an ER gap is charged its true path length rather than its straight-line length. Everything else — off-ER source, off-ER target, unreachable partner, or an along-ER detour longer than R — is forbidden (Inf). This fixes both blind spots of the straight-line proxy: it stops over-penalizing a link whose straight line happens to cut across a concave ER bay, and stops under-penalizing one that merely skims the ER edge. λ is unused here except in d0.

Gap closing gets the same treatment. A bridge must be reachable along the ER: both endpoints on their own frame's ER and connected along it within G — literally the same cost function the linker uses, with the gap radius substituted. So a gap close can never make a jump that frame-to-frame linking would have refused.

Strict mode fails CLOSED. A frame whose ER mask is missing, or present but all-false (what a segmenter returns when it finds nothing), contributes no tracked detections at all. It must never be read as "no constraint here", which would silently degrade the strict rule to unconstrained Euclidean linking for exactly the frames you know least about. You get a console warning (spt_track:noErMask), a log line, and two numbers in the settings file: tracking.frames_no_er_mask and tracking.dets_off_er. Both empty-mask and missing-mask frames are counted, so the provenance can distinguish "the ER genuinely covered every frame" from "the segmentation came back empty".

A cell with no ER segmentation at all is a different case: it is downgraded to Euclidean once, explicitly, at the top of the run — rather than letting an all-empty support array make strict mode (correctly) forbid everything and return zero tracks. The settings file then records the effective mode plus tracking.link_mode_req, the mode you asked for.

The 1 px registration slack

The SPT channel and the ER channel are acquired separately, so they can sit a fraction of a pixel apart. Every strict on-ER test therefore runs against the ER mask dilated by 1 px — spt_er_support, a single function that the strict cost matrix, the detection pre-filter and the gap-close reachability test all call, precisely so those three can never drift apart. Its rule, in its own words: a spot 1 px outside the segmented ER is still "on" it; 2 px is not.

At the reference pixel size of 0.10785 µm/px that slack is worth ≈ 108 nm (and the 2 px that is not tolerated, ≈ 216 nm). It is a registration allowance, not a biological one — if your two channels are misaligned by more than about a tenth of a micron, fix the registration rather than reaching for a looser mode.

Two different dilations exist, and they are not interchangeable: the strict support is the ER dilated by strel('disk',1), applied inside the geodesic cost function; the penalty mode's off-ER fraction is measured against the ER dilated by strel('diamond',2), prepared once per frame when the masks are loaded. Soft mode is deliberately the more forgiving of the two.

Off-ER detections, blank TRACK_IDs, and the localization cloud

_spots.csv vs _spots_filtered.csv — what actually differs

Short answer: nothing, except the TRACK_ID column. The two files hold the identical set of detections — same SPOT_IDs, same coordinates, same measurements. The filter does not remove rows; it un-assigns the detections belonging to tracks it dropped, blanking their TRACK_ID, and renumbers the survivors 0…K−1.

The near-identical file sizes are the giveaway: the filtered file is not a subset, it is the same cloud with 35,102 more blanks in one column. The XML pair is the opposite — _tracks.xml holds 5,564 tracks and _tracks_filtered.xml holds 273, and that one is a genuine subset.

Why keep the whole cloud? Tool 3's contact-site density is built from every detection, tracked or not. A molecule visible for three frames still says the ER was there. Discarding it for failing to form a long track would bias the density map toward wherever tracking happened to work well — which is exactly the regions you are trying to measure. So the filter is a statement about which trajectories you trust, never about which localizations are real.
The trap in the numbers. Because the cloud is preserved, filter.n_spots_written equals result.n_spots and tells you nothing about the filter. The number that answers "how much data came through this stage?" is filter.n_spots_in_kept_tracks — 27,194 against 116,092 on the cell above.
Where the blanks in _spots.csv come from

53,796 detections were in no track at all before any filtering. Sampled across 301 frames of that cell, they split roughly:

  • ≈41 % off the ER — excluded up front by strict geodesic, and counted in tracking.dets_off_er (23,131 on this cell);
  • ≈59 % on the ER but never linked — too isolated for the link radius, or present for only a frame or two.

Under Euclidean or ER-penalty the first group disappears (nothing is excluded up front) and every unlinked detection falls into the second.

Which pair Tool 2 reads. build_trackstruct defaults to 'Prefer','auto', which takes the _filtered pair whenever it exists and falls back to the raw pair otherwise. So the surviving tracks are what gets built into the TrackStruct, while the full detection cloud rides along with them for the density.
The localization cloud is never filtered. At every stage of Tool 1, tracks are filtered and detections are preserved. A detection that is not in a track — because nothing was in range, because the length filter dropped its track, or because ER-geodesic excluded it as off the ER — stays in the spots CSV as a full row with all its measurements, and only its TRACK_ID is blank. Nothing is deleted.

So there are three distinct populations in a single _spots_filtered.csv, distinguished only by TRACK_ID:

  • numbered — in a track that survived the filter;
  • blank, was tracked — in a track the filter removed;
  • blank, never tracked — unlinked, or excluded up front by strict geodesic.

This matters downstream in two ways. First, it means the strict ER rule costs you tracks, not data: the 653 detections geodesic excluded on the reference cell are all still in the CSV, available to anything that wants the raw localization distribution. Second, it means a raw row count is never a measure of how much the filter removed — filter.n_spots_written equals result.n_spots by construction. Use filter.n_spots_in_kept_tracks, or the log's "→ N tracks kept" figure.

Why a tracked spot can still look outside the ER on screen

You will see this, and it is usually not a bug. Two separate causes:

1 · The 1 px registration slack. Every strict on-ER test runs against the ER mask dilated by 1 px, so a localization up to one pixel — ≈ 108 nm at 0.10785 µm/px — outside the drawn ER boundary is legitimately "on" the ER as far as the linker is concerned. The overlay draws the undilated mask, so those spots sit just outside the visible edge. Beyond 2 px they would have been excluded.
2 · A multi-frame path drawn over one frame's mask. This is the bigger effect and the one that fools people. A track spans many frames, but any overlay shows the ER at one instant — and the ER moves. A segment the particle traversed at frame 900, drawn on top of frame 950's mask, can lie squarely in a hole that did not exist when the particle was there. Nothing was linked incorrectly; you are comparing a path from many times against a mask from one time.

Both ER tests — the soft penalty and the strict geodesic gate — are evaluated per frame, against the contemporaneous ER. So judge on-ER-ness the way the linker did: play the track in the embedded player with the ER overlay on, and watch the moving head marker against the current frame's ER. Do not judge it from the static path. If the head sits on the ER frame after frame, the track is on the ER, whatever the still image suggests.

A third, rarer cause worth ruling out: an inverted ER mask. If spt_load_seg warned that the foreground covers more than 90 % of the field, the label was read the wrong way round, and strict linking will have enforced the constraint against the complement of the ER — keeping precisely the off-ER detections. Check that warning before concluding anything about the biology.

Cells load themselves — there is no file picker

The section header reads CELL  (auto-loaded from the project tracks/ folder), and that is literal. When the tab is built, the app hands the viewer the project's tracks/ directory; the viewer scans it, pairs up the files, and loads the first cell immediately.

The old single XML+CSV picker is gone. It predated the Tool 1 → Tool 2 handoff and its only real use was to let you load a mismatched pair — an XML from one run with a CSV from another. Everything now comes from <project>/tracks/ — resolved from the app's top-bar project folder field (Tool 1 project folder (tracks/, er_seg/, mito_seg/)), falling back to the project folder itself if it has no tracks/ subfolder — so the tracks and the spots always belong to the same run. The Export and Batch output boxes are pre-filled with that same folder for the same reason.

What the scan looks for, in order:

  1. Tool 1's filtered pair — every *_tracks_filtered.xml in tracks/ (names containing builtin are skipped), each paired with the *_spots_filtered.csv of the same base name.
  2. Fallback — if the folder holds no *_tracks_filtered.xml at all, the raw *_tracks.xml + *_spots.csv pair is used instead (again skipping builtin and filtered names). So you can curate an unfiltered Tool 1 run, you just do not have Tool 1's length/displacement cut underneath you.

An XML with no matching CSV is silently skipped — a base name only becomes a loadable cell when both files exist. If nothing pairs up, the status line says so (No *_tracks_filtered.xml files found in the tracks folder. or Found *_tracks_filtered.xml but no matching *_spots_filtered.csv.).

The viewer never reads its own output. Tool 2 writes _curated; the scan only ever looks for _filtered or the raw pair. Re-opening the tab therefore always re-curates from Tool 1's result, not from your previous curation — your previous decisions come back from the in-session memory described under manual decisions, not from the exported files.

CROWDING — how local density is measured new

The crowding metric answers "is this track sitting in a busy part of the field?". It is worth understanding before you touch the threshold, because until recently it could not answer that question at all.

What was wrong. Density was counted within the linking radius, over tracked spots only. Both are wrong for this purpose, and measured on the reference cell the combination left the metric with no usable range: 73 % of tracks scored 0, the largest value anywhere in the cell was 2, and only 3 of 838 tracks could ever be rejected. Two thirds of the detections you can see on screen — 220,401 in the cell against 73,994 in surviving tracks — were invisible to it.
ControlWhat it does

Manual decisions and exactly what they survive

Your keeps and rejects are your judgement, and they are treated as outranking everything automatic. The kept set is always recomputed as

kept = (filter result \ manual_reject) ∪ manual_keep

so a manual decision is layered on after the thresholds every single time the kept set is rebuilt. Concretely, manual decisions survive:

  • A filter re-apply. Apply filter recomputes from the sliders and then re-imposes your overrides; the confirmation line reports how many were kept (… (2 manual overrides kept)).
  • Dragging the sliders. Even the un-applied Keep / Reject / Total preview is override-adjusted, and appends (2 manual overrides) so the number you read is the number you would get.
  • Switching cells and coming back. Overrides are stored per cell, keyed by base name, flushed whenever you navigate away, and restored on load — the load line says · restored 2 manual overrides when it happens.
  • A batch run. Batch filter flushes the open cell's decisions first, then for every cell re-applies that cell's own stored overrides on top of the thresholds. A batch can never silently overrule a decision you made by hand.

Toggling a track also clears the opposite override, so a track is never on both lists. The overrides live in the running app only — they are not written to disk except as the KEEP flags inside an export.

What stepwise bleaching looks like here, and why you care. A single fluorophore does not fade — it goes dark all at once. So one emitter gives a roughly flat trace at one level that drops abruptly to background and stays there. A staircase of more than one step is therefore direct evidence that the "single particle" you are looking at is not single — exactly the situation the displacement-variance metric is trying to catch, seen in a completely independent channel. Read it alongside panel 2: a step-displacement spike that coincides with an intensity level change is a mis-link you can be confident about; a smooth monotonic decay with no plateaus is more consistent with something other than single-molecule photobleaching (out-of-focus drift, for instance) and is not by itself grounds to reject.

Mislinkage repair — cutting a bad link new

The tracker sometimes joins two different molecules: one link in a chain jumps much further than the rest. Before this, the only remedy was the whole-track jump gate, which rejects the entire track for containing one bad step — so a 200-localization chain with a single mislinkage was thrown away whole. Now you can cut the link instead, and both halves are kept and judged on their own.

Why a horizontal strip and not TrackMate's TrackScheme. TrackMate needs a two-dimensional node graph because its tracks can branch — it models split and merge events. Ours cannot: spt_track links frame to frame with matchpairs, a one-to-one assignment, and gap closing consumes each candidate start once, so every track is a simple path. With no branching there is nothing for the second axis to show, and a strip along time can share the step plot's axis instead — which is what makes the spike and the link the same object.
Why the flag is relative, not an absolute distance. The obvious detector — "step longer than the gap-close distance" — does not work on real data. On the WithER cell the steps run 0.2–0.8 µm against a 1.40 µm gap-close setting, so it flags 0 links in 0 tracks: a track that visibly joins two separate clusters is never offered to you. What marks a mislinkage is that the step is an outlier for its own track — a molecule stepping 0.16 µm at a time does not take one 0.9 µm stride. So a link is flagged when its step is ≥ N × that track's own median step (N is yours to set, default 5) and at least half the linking distance, or when it simply exceeds the gap-close distance.

Both halves of that rule matter. Ratio alone at 3× flags 649 of 838 tracks on the reference cell — not triage, just noise, because a nearly stationary track has a median step near the localization precision and every jitter is a large multiple of nothing. The absolute floor is tied to the linking radius rather than fixed in µm, so it travels between datasets. At the defaults the same cell yields 116 links across 99 tracks, which is a session's work rather than a hopeless list.

Before you build, the Import & Curate tab scores every imported track on two numbers and keeps a track only if it passes both sliders (plus the optional jump gate). This is the one control on the tab whose meaning is not obvious, so here it is in full.

These are mis-linkage filters, not biology filters. Both metrics ask a single question — could the linker have stitched the wrong detections together here? Neither one selects for confined, mobile, ER-resident or fast/slow molecules, and neither is meant to enrich a phenotype. 1 · Local density — how crowded the linker's search window was.

For every spot the app counts the other spots in that same frame within a radius R, where R is the Linking max dist (µm) field — i.e. exactly the frame-to-frame radius Tool 1's LAP linker actually searched. If that count is high, the linker had several candidates in range when it chose a partner, so any link made there has a real chance of being the wrong one. That is the whole logic: high local density = elevated mis-link risk.

The per-track value reported is the max over the track's spots — the single densest frame it passed through — deliberately not the mean. A track that spends most of its life alone but dips through one crowded moment can be broken by that one moment, and a mean would average the danger away. The slider is labelled Max density and the filter keeps tracks with density ≤ that value.

Because R defines the metric, changing Linking max dist re-measures every track immediately and rescales the density slider. The three tracking-parameter fields (link dist, gap-close dist, max frame gap) auto-fill from Tool 1's <base>_settings.txt (tracking.link_um, tracking.max_gap_um, tracking.max_gap_frames), so by default the crowding radius already matches the run that produced the tracks. If a cell has no settings file, check the fields by hand.

2 · Displacement variance — is this one molecule or two?

Take the track's step lengths d (consecutive localizations, in µm) and report their variance. A clean single molecule diffusing has fairly consistent step lengths, so its variance is low — even a fast molecule, as long as it is uniformly fast. A track that has jumped between two different molecules instead shows a mixture: many small steps while it follows one molecule, plus the occasional large step where it hopped to the other. A mixture of scales inflates the variance far more than either population alone would, which is what makes this a mis-link detector rather than a speed filter. The slider is labelled Max disp var and keeps tracks with variance ≤ that value.

Steps are taken between consecutive localizations of the track (sorted by frame), so a gap-closed step counts once, at its full length — it will look large, as it should.

The jump gate — Reject jumps > gap-close dist. Optional, off by default, and density-independent: it ignores crowding entirely. Tick it and any track containing a single step longer than the Gap-close max dist (µm) is rejected outright, because a step beyond the LAP search window cannot be a link the tracker legitimately made — it is the classic mis-link signature. It combines with the two sliders as an extra AND condition, so it can only remove tracks, never rescue them.
The percentile spinners are helpers, not thresholds. Disp var keep below p and Density keep below p take a percentile of the current cell's distribution and write the resulting absolute number into the slider — that is all they do (at p = 100, the default, they do nothing). Their label shows the value each percentile maps to on this cell, so you can see what you are about to set. The sliders hold the actual thresholds, and the absolute slider values are what Batch filter applies unchanged to every cell — the interactive keep/reject decision and the batch decision come from the same code path, so the "keep / reject / total" preview for a cell is exactly what the batch will export for it. Set the threshold on a representative cell with the percentile helper if you like, then read off the absolute value and treat that as your published cut-off; percentiles themselves are per-cell and would move the bar from cell to cell.

Both histograms in the middle panel show the distribution you are cutting — displacement variance on one, local density on the other (integer bins, since it is a neighbour count) — each with the current threshold drawn as a red dashed vertical line. Drag a slider and the line moves, so you can place the cut relative to the shape of the data instead of guessing. Tracks whose metric is undefined (a single-localization track has no step, hence no variance) are kept, not silently dropped.

The build row

Time unit — frame or seconds

Sets what goes into matrix(:,:,1), the time page of the track matrix:

D fit — Fixed % vs Adaptive R², and the fit % spinner

These two controls decide how many MSD lags each track's straight-line fit uses. They drive both the per-track fit you see when you click a track and the pooled D-distribution histogram, so the histogram always shows D at the window you are actually looking at.

ModeWindow chosen
Fixed % (default)The same fraction for every track: m = round(lagN · fit% / 100) lags, where lagN is the largest frame lag at which that track has at least one pair. Clamped to 2 ≤ m ≤ lagN, so at least two lags are always fit.
Adaptive R²Per track, the largest window that still fits with R² ≥ 0.95, using at least 3 lags and at most the fit % above. Under the hood it sweeps every window from 2 lags up to that cap and takes max(npts) among those clearing the threshold; if none clears it, it falls back to the most linear window (highest R²). A track that stays linear therefore uses many lags, a confined or directed one uses few — some 10 %, some 25 %.

The fit % spinner is 5–100, default 25, step 5. In Fixed % mode that is the window. In Adaptive R² mode it is the maximum the adaptive search may use, and it is clamped up to 10 % — an adaptive cap below 10 % behaves as 10 %.

Changing either control re-fits everything and redraws, and it remembers the clicked track (by cell index and matrix column), so you can watch one track's D move as you change the window. Neither control touches the stored file — the fit is done live from the stored MSD; nothing is rebuilt and nothing is re-saved.

The percentage is of that track's available lags, not of its length. For a gap-free track of L localizations there are L−1 lags, so 25 % of a gap-free 100-localization track (99 lags) is 25 lags; a track that only reaches lag 40 gets 10.

confined ≤ D — the confinement threshold

A spinner in µm²/s: limits 0.001–100, default 0.15, step 0.05, displayed to 3 significant figures. It is a per-localization threshold — a localization whose stepwise D(t) is at or below it is flagged confined — and it defines the flags Tool 3's Confined and State-change density channels run on.

Changing it does not rebuild anything. The flags are re-derived from the stored Dt: confined = Dt ≤ threshold, and stateChange is recomputed as the rising edge into each confined run (walking each track's real localizations in frame order). That is arithmetic on an array already in memory — no re-rolling of the estimator, no re-parsing of XML. The new flags are written back into the active build (not unconditionally into TrackStruct.mat, which used to leave a divergent shadow file behind), diffOpts.confineD is updated so the provenance matches, and the QC redraws.

Because NaN ≤ x is false, padded slots and gaps are never flagged confined. What the spinner cannot change is Dt itself — the window, the mode and the noise floor σ are fixed at Build (see below); to change those you rebuild.

Confinement and state changes — not currently in the pipeline

Builds store the rolling diffusion only. Tracks.confined and Tracks.stateChange are no longer written, and Tool 3's contact-site picker no longer has Confined / State-change density channels — its density is always the tracked localization cloud.

The reason is that every one of those flags depends on a confinement criterion, and picking contact sites by diffusion state would have rested on a parameter nobody was setting. Measured against a matched Brownian null on the reference cell, the criterion that had been shipping fired on 45 % of tracks with no state change at all, and on 95 % of tracks that were simply slow the whole time — so those channels were selecting largely on noise.

The capability is intact, not deleted: spt_confine_flags implements four criteria (segment, drop, relative, absolute) with the full benchmark in spt_track_diffusion's header. To bring it back, pass confMode &c to spt_track_diffusion and store Tk.confined / Tk.stateChange in the build. Old builds that still carry the fields load and display fine; they are simply ignored.

The two diffusion estimators — what each number means

Each step is weighted by the time it actually spans. diff() runs over localizations, not frames, so a gap-closed step covers more than one frame interval. Dividing it by a single dt attributes all of that displacement to one frame and inflates D by the gap factor. The estimator therefore pools numerator and denominator separately — D = ( Σr² − 4σ²·n ) / ( 4·Στ ), with τ the real elapsed time of each step — so every step contributes in proportion to the time it observed. With no gaps this is identical to the old <r²>/(4dt) − σ²/dt to floating-point precision.

Measured: on synthetic tracks with 10 % of frames dropped the unweighted form ran +11 % high, the weighted one +0.7 %. On the reference cell, where 3.2 % of steps span two frames (2,193 of 69,009), median stepwise D fell 2.8 % and the maximum 22 %; 19 % of localizations moved by more than 10 %, all of them gap-adjacent. Builds made before this need rebuilding to pick it up.

The tab shows two different D, and confusing them is the easiest mistake to make here. One is a single number per track from an MSD fit; the other is one number per localization from a rolling step estimator. They are computed differently, they answer different questions, and only the second one feeds the downstream flags.

1 · Per-track D from the MSD fit (drivers/spt_fit_msd.m)

Fit a straight line to the first m lags of the track's own time-averaged MSD:

MSD(τ) = 4·D·τ + b          (2D Brownian motion)
D       = slope/4                        µm²/s
σ_loc   = sqrt(max(b,0))/2               µm   (from the τ→0 intercept)

with τ = (1:lagN)·dt. The fit is an ordinary polyfit degree-1 least squares; R² is reported over the fitted points only (1 − SS_res/SS_tot), so it measures how straight the MSD is inside the window you chose — a low R² is telling you the window is too long for this track, not that the track is bad.

The intercept b = 4·σ_loc² gives a fit-free estimate of localization precision. Treat it as an upper bound: it also absorbs confined and motion-blur dynamic error within the first lag, and it moves with the fit window. That is why the app reports it only as a small trailing note on the clicked-track readout (· σ_loc≈NN nm) and never gates anything on it.

2 · Stepwise (per-localization) D (drivers/spt_track_diffusion.m, run at Build)

The native-MATLAB equivalent of run_step.py's noise-corrected rolling estimator. For every localization i of a track, take the single-step squared displacements dr² in a rolling window centred on it and subtract the localization-noise floor:

D = <dr²>/(4·dt) − σ²/dt          floored at 0
                                  (because <dr²> = 4·D·dt + 4·σ² in 2D)

The rolling window is win = 7 localizations — for localization i the estimator averages the steps from i−3 to i+3, truncated at the ends of the track (so the first and last few localizations average fewer steps). The window is in localizations, not frames, and it is not exposed in the UI. Tracks with fewer than two localizations get no D at all. A second mode ('msdfit', a local MSD slope over up to 4 lags inside the same window) exists in the driver but the app always uses the default 'lag1'.

Where σ comes from: the top bar's Loc prec nm field (default 30 nm), divided by 1000 → sigmaUm. dt is that cell's frameInterval from the tracks XML when it is present and positive, otherwise the top bar's dt s (default 0.020064). Both are frozen into diffOpts at Build, so a stored build always records the σ and dt it was computed with.

The floor at 0 matters when reading the histogram: wherever the local mean step MSD sits below the noise floor the estimate is exactly 0, so a spike at 0 is expected and means "not resolvably mobile at this σ", not "measured to be still".

stateChange is the rising edge into a confined run — mobile at one localization, confined at the next — i.e. a fast→slow entry, a capture event. It is deliberately not symmetric: an exit is not flagged.

Check dt before you trust any absolute D. The per-cell frameInterval read from the XML root wins over the top-bar dt s everywhere D is computed — and when the XML carries no frameInterval attribute the importer stores 1 (one second per frame). A build made from such an XML will report D values scaled by that wrong dt. Use Auto in the top bar to read frameInterval out of a tracks XML and confirm it is what you expect.

CSD — cumulative displacement

Cumulative path length in µm against step number, one faint orange curve per track, the median bold, and the clicked track highlighted in orange on top. Title: "CSD — <n> tracks · median total <µm> µm · median to step <k>", where median total is the median of each track's final value.

Why the bold median stops. At step k the median can only be taken over the tracks that are still alive at step k. Past the bulk of the length distribution that is a handful of unusually long tracks, and since long tracks have travelled further the median drifts upward — pure survivorship, not a change in behaviour. So the median is drawn only while at least max(5, 10% of tracks) still contribute, and the title reports exactly how far that is ("median to step <k>"). Beyond that point the faint curves are still shown; the summary line deliberately is not.

The x axis is step number, not time. For a gap-free track step k is k frames, but a gap-closed step spans more than one frame while occupying one step slot.

CSD is a distance, and it was corrected. It is cumsum of the actual step distances |r(t+1) − r(t)| in µm, so a gap-closed step contributes its full length. It previously summed dS/dT — a per-frame speed — which charged a two-frame gap only half the distance the molecule really covered, and was not even in µm unless every dT was 1. On the reference cell, where 86.6 % of tracks contain a two-frame gap, total path length was understated by a median of 2.0 % and up to 11.5 % per track. If the build predates the diffusion pass the panel says "stepwise D(t) — not in this TrackStruct".

This is the panel that shows what the single per-track D hides: a molecule that diffuses, gets captured, sits, and leaves has one MSD-fit D that describes none of those phases, and three visible regimes here.

The TrackStruct contract — every field, and what it holds

The build is a 1 × nCells struct array called Tracks, one element per cell. Field names and shapes are a contract: Tool 3, the picker, the mapper and the pristine ContactSites suite all read them directly, and the suite freezes file, matrix and vector in particular.

The padded [nF × nT] layout. Every per-localization field is a dense rectangle: nT columns = tracks, nF rows = the length of the single longest track in that cell. Shorter tracks are padded, and NaN means "no localization at that frame slot" (logical fields pad with false). Per-step fields are [nF−1 × nT]; a track of length L has L−1 real step rows and padding after.

The cost is real but bounded: bytes ≈ 200 · nF · nT per cell. On the reference cell (838 tracks, nF 381, 73,994 localizations) occupancy is 23.2 % — 11.9 MB on disk, 70.7 MB resident, 66.5 % of that NaN padding, loading in 51 ms. nF does not run away because photobleaching bounds track length, so the padding is a roughly constant ~4× overhead rather than an explosion risk. The importer warns if a cell's padded layout looks pathological (over ~250 MB, or under 10 % occupancy and over 60 MB).

Do not "optimise" nF away. nF is the column stride of persisted linear indices: the mapper stores find(...) results as each site-window's LocIDs in CSW_final.mat. Change nF — by trimming padding, or merely by re-curating to a different longest track — and every stored index silently points at a different localization. That is why re-curating means re-running the downstream stages, not reusing old ones.

Working practices

  • Build once, per curation. The MSD pass is the expensive step in the whole pipeline. Everything on this tab except Build itself — both fit controls, the confinement threshold, the cell selector — is a live recompute or a cheap re-derivation, so explore freely without rebuilding.
  • Name every build you intend to compare. Day1_WT / Day1_KO beats one TrackStruct.mat you keep overwriting, and it lets the same folder carry both. Leave the name at TrackStruct and nothing changes: a project with no pointer falls back to TrackStruct.mat.
  • Confirm which build is active before you analyse. The top-bar Build dropdown's ● is the authoritative answer, in both tools, and the Experiment tab's built lamp resolves through the same pointer.
  • Re-curating invalidates downstream results. A new build can change nF, and stored linear indices in CSW_final.mat are strided by nF. Re-run the picker, the mapper and Dwell rather than trusting files from the previous build.
  • A rebuild does not clear downstream state — you must. ▶ Build + QC is the one path that leaves the in-session Refine footprints, Sites mapper results, Dwell results and density/null caches standing: 📂 Load TrackStruct…, the top-bar Build selector and a change of project folder all reset them, but Build does not. Since a rebuild is precisely the operation that can change nF, re-run the downstream stages after building instead of reading the panels still on screen.
  • Sanity-check a fresh build in this order: cell table (are all cells there, do mito/ER show ✓) → the on-ER % in the readout line → track length (does the left edge match Tool 1's min-length filter) → D distribution median against the sweep panel of two or three clicked tracks → the stepwise histogram, to place the confinement threshold. Only then move to Tool 3.
  • MATLAB apps do not hot-reload. If you edit a source file mid-session, close and relaunch — a stale figure throws phantom callback errors.

⇢ Sweep window length

Runs detection at several candidate window lengths and pops up a Window-length sweep figure so you can see where the answer stops depending on the window. Concretely: it tries 1, 2, 4, 8 and 16 non-overlapping windows (i.e. frames/win = round(T/K), dropping any below 50 frames), and for each detects in every window and records the total number of sites and the median site significance.

  • Left axis, solid: # contact sites detected summed over all windows, each point annotated with the window count.
  • Right axis, dashed: median site significance 1 − p.
  • x axis is frames/window on a log scale, with a dotted vertical line at your current setting.
  • The text row underneath spells out each point: fpw N: k win · ~L loc/win · S sites · med sig X — the loc/win figure is what tells you whether a window length is starving the density.
The sweep is an approximation, and deliberately so. It uses the whole-movie ER support instead of each window's start-frame ER mask, a cheaper 80-run Monte-Carlo null (or your sims value if lower), always the full tracked set (it ignores the channel dropdown), non-overlapping windows only, and it does not apply your min enrich or min tracks gates. Read it for the shape — where the curve flattens — not for the site counts you will finally report.
Read the sweep right-to-left (long windows → short). Your minimum usable window is the last point before either the site count starts falling or the median significance drops. On the reference cell it is flat (16–23 sites, significance ≈ 1.0 down to about 6,800 loc/win), which means that cell is not localization-limited: pick the window length from how fast the sites move, not from counts.

The density channel — removed

There used to be a channel dropdown here offering Confined (low D) and State-change, which built the density from a diffusion-state subset of the localizations instead of all of them. It is gone: the density is always the tracked localization cloud.

Both channels read Tracks.confined / Tracks.stateChange, which builds no longer write. Those flags depend on a confinement criterion that is not currently part of the pipeline, so selecting contact sites by diffusion state would have rested on a parameter nobody was setting — and the criterion that had been shipping fired on 95 % of tracks that were merely slow throughout, so the channels were selecting largely on noise. See Confinement and state changes for how to bring the capability back.

method · sens · sims — how the cutoff is set

Detection thresholds the σ-smoothed density and is confined to the ER support of the window (a site must sit on the ER). Three methods, chosen with method; sens means a different thing in each, and its default changes when you switch:

sims (default 300, range 20–2000, step 20) is the number of Monte-Carlo runs. The finest resolvable p is 1/sims, so 300 runs bottom out at p ≈ 0.0033. More runs also steady the extreme quantile that sets the cutoff — with too few runs the (1−α) quantile itself is noisy and a window can collapse to a couple of sites for no biological reason. The ER support the null scatters within is the ER segmentation at that window's START frame, resampled to the density grid — so a moving ER is handled per window rather than by a whole-movie projection. If that frame's mask is missing or empty, the picker falls back to the whole-movie ER MIP (thresholded at 5 % of its maximum); if there is no MIP either, the support is the whole grid. The null draws N = the on-ER localization count of that window, from a fixed seed, so browsing back and forth gives the same numbers.

Grid and scale: the density grid is the height of a saved Densities/*_rho.tif, else ceil(FOV ÷ bin) — with the default FOV 27.61 µm and 30 nm bin that is a 921 × 921 grid at SF ≈ 0.030 µm per density pixel. Smoothing is σ = 8 density px. All site coordinates in the picker, its table, and the saved _CSsites.txt are in density pixels, not camera pixels and not µm.

The automatic outline — frac and maxR

The default outline is half-max: take the maximum density within a disk of radius maxR around the pick, keep the connected patch of density ≥ frac × that local peak which contains the pick, clip it to the disk, and trace its outer ring.

SpinnerDefaultEffect
frac0.5 (0.1–0.95, step 0.05)The contour level as a fraction of the local peak. Lower frac = bigger site (you are cutting further down the flank); higher = a tighter core. 0.5 is literally half-max.
maxR0.6 µm (0.1–3, step 0.1)Hard size cap: the outline is clipped to this radius about the pick. 0.6 µm is a deliberate physical prior — an ER–mitochondria contact is sub-micron. Raise it only if you can see the site really is bigger.

✎ Draw centre + boundary — the manual refine

This is the paper's mouse-driven refinement. The prompt walks you through two clicks:

  1. Click the CENTRE. The point you click becomes the site's centre — it does not have to be the original pick, and the mapper will honour your moved centre while still matching the site by its original pick position.
  2. Press and drag to trace the BOUNDARY. Freehand. Esc (or releasing without a real trace) cancels; the status line tells you which stage cancelled.

The traced polygon is stored in µm relative to the centre you clicked, and the closing seam is tidied: a freehand trace closes with a straight chord back to the start, leaving a sharp notch, so a light corner-rounding pass is applied to only the four vertices either side of the seam (three gentle Laplacian passes). Every other vertex you drew is kept exactly as drawn. The mode becomes freehand and the site is flagged edited.

Closing the seam is not the same as smoothing the outline. If you want the whole shape rounded, use ✨ Smooth boundary below — it is a separate, explicit action.

✨ Smooth boundary

A half-max ring traced from pixels is jagged by construction, and a freehand trace is jittery. ✨ Smooth boundary turns either into a clean closed curve: the polygon is resampled to 120 points equally spaced by arc length around the loop, then x and y are run through a periodic (wrap-around) moving average, so there is no kink where the curve closes.

The smooth boundary slider (0–1, default 0.35) sets the strength by growing the averaging window — 0 keeps the detail, 1 is nearly a circle. Each click smooths further (they compound), the area is recomputed by polyarea each time, and the site's mode gains a +smooth suffix — halfmax+smooth, freehand+smooth — so the title records what you did.

Smoothing changes the area and therefore changes membership, enrichment and dwell downstream. Smooth for a defensible shape, not for a prettier picture, and keep the strength consistent across the sites in a dataset.

The radial plot and its cell-wide ER-uniform reference

Beneath the editor, the radial concentration panel answers a different question from the detector's: do these localizations actually pile up toward the centre? It plots, for growing radius r out to 1.2 µm, how many localizations lie within r of the centre (solid, filled) against a dashed reference (x axis in nm).

The dashed line is not a disk of local density. It is the cell-wide ER-uniform expectation:

ρ      = (localizations on ER, whole cell) / (total cell ER area)   % locs per µm² of ER
ref(r) = ρ · A_ER(r)                                               % A_ER(r) = ER area within r of the centre

Both terms come from the cell's ER mask resampled onto the density grid, using the same round(µm/SF) transform the density uses, with A_ER(r) evaluated at 60 radii. So the reference already accounts for the fact that there is more ER in some directions than others — the solid curve sitting far above it means genuine enrichment above the cell's own ER background, not merely "there is ER here". The legend says which reference is in force: uniform over ER (cell density), or uniform (random) when it falls back.

The single number in the title, concentration, is max over r of (observed count − reference count) ÷ n — the largest excess over the null as a fraction of the localizations in view. Roughly: 0 = tracks the null (diffuse), →1 = tightly central, <0 = below the cell-wide ER background. On the busiest reference-cell site the ER null is about 9 localizations within 1.2 µm against 670 observed — around 75× enrichment.

If the cell has no usable ER occupancy, or there is no ER within the window around the site, the plot silently falls back to the legacy disk-uniform null n·(r/R)² and the legend changes to uniform (random). That version says nothing about the ER, so read the legend before quoting a concentration index. With fewer than 3 localizations in view the panel just says so.

What a good — and a bad — boundary looks like

Good.
  • The outline hugs one density peak, and with show localizations on it clearly encloses a compact cluster of points rather than empty smoothed halo.
  • Mode reads halfmax (or halfmax+smooth) — the automatic trace succeeded.
  • Area is well under the maxR cap, i.e. the shape stopped because the density fell off, not because it hit the disk edge.
  • The radial curve rises steeply then flattens, sitting far above the dashed ER reference; the concentration index is well above 0.
  • A healthy fraction of the window's localizations is inside, and the member trails visibly linger rather than shooting through.
Bad — and what it means.
  • Mode says box — the half-max trace failed (empty, tiny, or truncated at the FOV border). The square outline is a placeholder, not a measurement. Draw it by hand or drop the site.
  • The outline is a disk clipped exactly at maxR — the density never fell to frac × peak inside the cap. Either the site really is larger (raise maxR knowingly) or the pick sits on a broad ridge rather than a site.
  • The outline swallows two peaks. Re-detect with split peaks on, or raise frac to separate the cores.
  • The radial curve tracks the dashed line and the concentration index is near 0 — the localizations are just accumulating with area, exactly as a uniform ER density would. That is a diffuse patch, not a contact site; consider deleting it.
  • Very few member tracks despite a bright peak — one parked or blinking molecule. This is what the min tracks gate exists to reject.
  • The boundary drifts off the ER (turn the picker's ER overlay on to check) — suspect registration or a spurious peak.

Tool 3 · Dwell — residence times and escape rate

Tab 5 · Dwell converts membership into time: how long each molecule actually stayed inside each contact site, and how fast molecules leave.

What a dwell event is

A dwell event is a maximal run of consecutive in-footprint localizations of one member track, clipped to that site's own window. Its duration is

dwell = (exitFrame − entryFrame + 1) · dt

Three things follow from that definition, and all three are deliberate:

  • Frame-span accounting, not step counting. A single in-footprint localization is a dwell of one frame (dt), not zero.
  • One track can produce several events at one site. Leave and come back and you get two events, which is exactly what makes an escape rate meaningful.
  • Clipping to the window is what makes residence time-resolved. A footprint is only valid for the window it was detected in, so residence is never measured with a boundary that did not exist at that time.

The inside test, the run-finding, the interval merging and the classification are lifted verbatim from the paper suite and must not be re-derived — they encode the conventions above.

▶ Compute dwell needs CSW_final.mat (it loads it from disk if this session has not run the mapper) and reports, when done:

The two plots

  • dwell-time distribution — a histogram of every event's duration in seconds, on a log y axis (short events vastly outnumber long ones; a linear axis hides the tail that actually matters). Bin count adapts to the sample size. The title carries the median and n: "dwell-time distribution (median 0.12 s, n=1184)".
  • escape rate kout(window) — one bar per window of k_out(w) = nEvents(w) ÷ Σdwell(w), in s−1: the inverse mean residence time for that window. The title gives the pooled value over all windows. This is the time-resolved headline — if k_out falls across windows, molecules are being held longer as the movie progresses.
k_out is a ratio of pooled quantities, so a window with only a handful of events can produce a wild-looking bar. Cross-check the event count for that window (the per-track table, or the events CSV) before reading anything into it.

Scanning is cheap by construction. The 20 MB *_spots.csv files are never row-counted. What the counts show you that a lamp cannot

A lamp answers did this step run? The counts answer on how much data? — which is the number that decides whether a cell is worth analysing at all. Two cells can both show tracked ✓ curated ✓ built ✓ and be nothing alike:

Reading a row as an attrition chain. Scan left to right along spots → tracks → filt → cur → in build and look for the step where the number collapses.
  • spots high, tracks low — the linker is not finding trajectories. Check the linking distance and mode on Tool 1's Track & filter tab.
  • tracks high, filt tiny — almost nothing reaches the min-track-length cut, so the movie is bleaching out or the detections are noise. Compare against a healthy cell before you spend time curating it.
  • filt healthy, cur tiny — Tool 2's curate thresholds are cutting hard on this cell. Because those thresholds are absolute and applied unchanged to every cell in a batch, one crowded cell can be gutted by a cut that suits the others.
  • cur healthy, in build shows – — this cell is not in the active build, even though the folder's built lamp is ✓ (that lamp is folder-level). Either it was built into a different named build, or it was added after the build ran. Rebuild, or switch the active build in the top bar.
  • in build fine, trk spots low — the surviving tracks are short. Density, contact-site detection and dwell all live off localizations, not tracks, so this is the count that predicts whether a cell has the statistical power for Tool 3.
A cell that shows tracked ✓ with 6 surviving tracks looks exactly as healthy as one with 800 if you only read the lamps. That is the single reason the count block exists — read it before you commit an experiment to a condition mean.

Exclude and notes

✖ Exclude toggles the QC-exclude flag on the selected rows (same effect as ticking the excl box). The tooltip states the semantics: excluded cells "drop from analysis but stay recorded" — the row, its counts and its notes remain, so a rejection is documented rather than deleted.

Use notes to record why — drift, a dying cell, a bad ER segmentation — so the exclusion survives your memory.

The filter box

The filter field (placeholder condition / day / cell / 'unassigned' / 'unmapped') does a case-insensitive substring match against a keyword blob assembled per row from:

  • the day, the cell base name and the condition;
  • the names of the stages that are true — so typing built keeps the built cells, dwelled the dwelled ones;
  • excluded when the row is excluded;
  • unassigned when the condition is blank;
  • unmapped when not mapped, undwelled when not dwelled.

So unassigned is the fastest way to find cells you have not labelled yet, and unmapped the fastest way to find folders that still need the mapper. The summary line

The label to the right of the buttons is the status line. Before you add anything it reads Add each day's folder, then assign conditions. Status is read from the files. After a scan it becomes a one-line census of the whole experiment:

<N> cell(s) · <N> folder(s) · <N> mapped · <N> condition(s) · <N> spots · <N> tracks linked → <N> kept.

Reading it left to right: cells in the table; folders scanned; cells whose folder is mapped; distinct non-blank conditions; then the pooled attrition tail — total spots and total tracks linked summed across every cell that reports them, and kept = the total after curation (falling back to the after-filter total when nothing has been curated yet). Cells with no value for a count are skipped rather than counted as zero, and the tail is omitted entirely when nothing is countable. It is a sanity check, not a result: if the spots total halves after you re-run something, you have changed more than you meant to.

The project picker — what setting a project actually does

Type a path into the field (placeholder Tool 1 project folder (tracks/, er_seg/, mito_seg/)) or use Pick…. Setting a project is a single deliberate reset, and it does all of the following in order:

  1. resolves the tracks folder to <project>/tracks, or the project folder itself if there is no such subfolder;
  2. drops the previously loaded build and resolves the new folder's active build name — so carrying Day1_KO.mat into the next project cannot open the wrong build;
  3. clears the per-project density cache and resets all downstream state — sites, footprints, mapper results, dwell results, the Monte-Carlo null caches, the Refine/Sites/Dwell panels. Nothing from the previous project can leak into the new one;

  5. reads the project's calibration — pixel size, frame interval and field of view — from what Tool 1 recorded, and writes cs_calib.mat only if it found something;
  6. (Tool 2) embeds the Import & Curate viewer on the tracks folder;
  7. points the Experiment panel at <project>/experiment_details.mat and adds <project>/analysis to the manifest;
  8. refreshes the Build selector.

How the aggregation works across folders

In experiment mode, cs_experiment_aggregate walks the unique folders of the manifest and, for each one:

  1. loads CSW_final.mat if it is there, drops the sites belonging to excluded cells, then stamps every remaining site with its cell's condition (blank becomes (unassigned)) and its srcFolder;
  2. loads cs_window_dwell.mat if it is there and does the same to DD.events and DD.perSite;
  3. concatenates everything into one combined CSW and one combined DD, harmonising fields across sources (a field missing from one folder is filled with []), and rebuilds DD.allDwell as the pooled event durations.

Condition and exclusion are matched on the (folder, cell) pair, so two days that happen to contain a cell of the same name stay distinct. A folder with no CSW_final.mat — or an unreadable one — is silently skipped, which is why the Experiment tab's mapped lamp is worth a glance before you compare: a missing lamp is a folder that will contribute nothing.

Only results are pooled, never raw tracks. The aggregation touches CSW_final.mat and cs_window_dwell.mat — per-site and per-event records, which are small. No TrackStruct is loaded, let alone merged. That is what makes a hundred-cell comparison cost the same memory as a one-cell one; see Scale.

Reading the output

  • The table — one row per group: group, n, mean, sem. Groups appear in first-seen order, not sorted.
  • per-site values by group — every site plotted as a jittered dot with a red dash at the group mean. Look at the spread, not just the dash: a mean difference carried by three outlier sites is visible here and invisible in the table.
  • pooled dwell-time CDF — one stair per group over the pooled event durations of that group (events carry window, mito flag and condition directly, so the CDF is grouped the same way as the table). It is drawn whenever dwell events are loaded, whatever metric you chose; with none loaded the title says so.
  • The status line — enrichment by condition · 2 groups, and when there are exactly two groups and the Statistics toolbox is available, a Wilcoxon rank-sum test on the per-site values is appended: · rank-sum p=0.0031.
The p-value treats site-windows as independent. Sites from one cell are not, and overlapping windows of one site certainly are not. Use it to triage, then do the real statistics with the day/replicate labels from the manifest as your unit — that is what the day/rep column is for.

Density & counts (tracked-only)

A contact site is a place where the protein concentrates, so everything downstream is built on a localization-density map. Two rules matter:

The density is always built from TRACKED localizations — spots that belong to a track. Single-frame detections (noise, blinks) are excluded. For WithER: 73,994 tracked localizations out of 220,401 total detections, so 66 % of the raw cloud never enters the density. Not all of that is noise — it is every detection that ended up in no surviving track, which on this cell is dominated by tracks that were real but too short to clear Tool 1's min-length 50 gate (raw tracking had linked 194,439 of the detections; the length and displacement filter is what cuts it to 73,994). Single-frame blinks and spurious peaks are a part of the remainder, not the whole of it.

The picker always shows all three counts so you know what you're looking at:

The clauses, in order: the cell file; the total detections in allSpots; the tracked count that feeds the density, with its percentage of the total; the window count; whether per-spot mito distance came from the CSV's MITO_DIST_UM or had to be derived; and — once a window is drawn — that window's own tracked count. Two clauses appear only conditionally: · channel <mode> (N locs) when the density channel is not the default tracked, and · N of M windows ⚠ frames K+ NOT analysed in place of the plain window count when the 24-panel cap has cut the movie short. The density map, in code

% bin tracked localizations (µm) whose frame is in [t0,t1] onto the grid, then Gaussian-smooth
Lx = round(X/SF);  Ly = round(Y/SF);            % µm → density pixel  (SF = FOV/grid)
counts = accumarray([Ly Lx], 1, [H W]);          % row = y, col = x
dens   = imgaussfilt(counts, 8);                 % σ = 8 px detection scale

Windowing — and "how many localizations is enough"

Contact sites move and turn over, so the density is built per time window, not over the whole movie. Controls on the Contact-sites tab:

ControlWhat it does

Rough floors per window: <300 too noisy · 1–2k minimum · 5k+ confident · whole-movie best (static sites only).

Find your minimum with the sweep: read it right-to-left (dense → sparse); your minimum is the loc/win at the last point before # sites drops or significance falls below ~0.9. For WithER the sweep is flat (16–23 sites, significance ≈ 1.0 down to ~6,800 loc/win) — that cell is not localization-limited, so window length is chosen by how fast the sites move, not by count.

The Monte-Carlo null & significance

How do we know a bright patch is a real site and not a random clump? We compare it to a null: if the same number of localizations were scattered at random over the ER, how bright would the brightest chance-peak be?

% cs_mc_threshold: M random realizations, keep only each run's PEAK smoothed density
for m = 1:M
    sel = randOnMask(N);                     % scatter N points over the ER mask
    Dm  = imgaussfilt(accumarray(sel,1), 8); % smooth the SAME way as the data
    nullMax(m) = max(Dm(mask));              % the brightest chance-peak this run
end
Dthr = quantile(nullMax, 1-alpha);           % detection cutoff (family-wise error ≈ alpha)
Why it's fast. The whole null is just M numbers (the peak maxima). A site's significance is then a lookup, not a new simulation: 
p = mean(nullMax >= siteDensity);   % fraction of chance-peaks at least as bright
Keeping only the max of each run builds the multiple-comparison (family-wise) correction in for free — one null covers every pixel at once. With M runs the finest resolvable p is 1/M (so 80 runs can't distinguish anything stronger than p ≈ 0.012).

The colorbar shows this null band + the cutoff; the "significance (p)" display recolours the map by per-pixel p.

Robust peak detection upgraded

The base detector thresholds the smoothed density, drops specks, and takes one centroid per blob. Several upgrades make it more trustworthy. All are on the Contact-sites tab; re-run Detect to apply.

Split merged peaks

Two real peaks that touch above the threshold used to collapse into a single centroid at the saddle. split peaks (on by default) runs a marker-controlled watershed so each prominent maximum becomes its own site.

mk = imregionalmax(imhmax(dens, h)) & bw;    % markers = peaks standing ≥ h above surroundings
I  = imimposemin(-dens, mk);                 % basins only at the markers
L  = watershed(I);                           % → one label per genuine peak

Effect-size gate — min enrich ×

A peak can be statistically significant yet trivially small. Require its peak density to be at least this multiple of the ER-median background. 1× = off. Concretely, on WithER a gate of 7× keeps 6 of 28 sites (enrichment 7–11×).

Distinct-molecule gate — min tracks SPT-specific

The subtle one. Density counts localizations, but one molecule parked at a spot for 500 frames dumps ~500 near-identical points and looks exactly like a busy site. This gate keeps a site only if at least this many distinct track IDs contribute — a real contact site is visited by many molecules. On WithER, requiring ≥16 distinct tracks cut 28 candidate sites to 13 (several had only 2–6 tracks).

Stability score

Each detected site gets a stab value (0–1): the fraction of random split-halves of the data in which the site's peak stays enriched in both halves. A real site scores 1.0; a one-off blip scores low. It's shown in the per-site table (no gating — you decide).

Alphabetical. Every entry gives the definition as the code computes it, the units, the file that computes it, and where you read it. Where two stages compute a similarly-named quantity differently, both are given — that is the single most common source of confusion in this pipeline.

Troubleshooting

Real failure modes, each one traceable to a specific guard, warning or fallback in the code. If MATLAB prints a warning identifier, find it here.

ER segmentation problems

spt_track:noErMask — "N of M frames have no ER mask, so every detection in those frames was excluded from tracking".

What happened. You ran ER-geodesic, and some frames had no usable ER support — either the ER stack has fewer pages than the movie, or the segmenter returned an empty mask for those frames. Strict geodesic fails closed: a missing mask means forbid, never "no constraint here", because reading it as no-constraint would silently degrade those frames to unconstrained Euclidean linking. So every detection in those frames is dropped before the assignment and contributes nothing — not to a frame link, not to chain assembly, not to a gap close.

Check. Compare page counts: the ER stack must have at least as many pages as the movie. The loader truncates to min(pages, nFrames), so a short ER stack leaves the tail of the movie with no support at all — and the same tail gets blank ER_DIST_UM. Then read the cell's _settings.txt: tracking.frames_no_er_mask is the count, and it deliberately lumps "no page" together with "page present but all-false", because otherwise the provenance line could not tell a fully-covered movie from an empty segmentation. tracking.dets_off_er tells you how many detections the on-ER test itself rejected.

What to do. Re-export the segmentation over the full movie, or switch that cell to ER-penalty, which excludes no detections at all. Do not treat a large frames_no_er_mask as cosmetic — those frames are simply absent from every track in the cell.

spt_seg_fg_label:uniformStack — "every sampled pixel has the same value, so there is no foreground/background distinction".

What happened. The pages sampled through the stack (up to 16, evenly spread) all carry one single value. There is no label map here: either every pixel matches the inferred foreground label (the whole field becomes "ER", and ER-aware linking silently stops constraining anything) or none does (nothing is ever on the ER). Neither is usable, so the code says so instead of failing quietly.

Check. Open the stack and look at it. A common cause is exporting the wrong ilastik output — a probability map rather than the Simple Segmentation, or a stack that was thresholded to nothing.

spt_load_seg:suspectInversion — "foreground covers N % of the field — the label map may be INVERTED".

What happened. The foreground label was inferred as the minimum non-zero value over a sample of pages spread through the stack (1 for an ilastik label map, 255 for a 0/255 binary) — deliberately not from page 1 alone, because an ilastik page that happens to contain no ER is entirely label 2, and reading the label off that page inverts every frame. The warning fires when the resulting mask covers more than 90 % of the field, which usually means the inversion happened anyway (or the segmentation is genuinely useless).

Why it matters most in geodesic mode. An inverted ER mask keeps exactly the off-ER detections and forbids the on-ER ones — the maximally wrong outcome, and a silent one. Never trust an ER-aware run that printed this warning.

A cell with no ER segmentation at all — the ER mode was downgraded.

What happened. No ER file was matched for that cell, so the requested ER mode was downgraded to Euclidean once, explicitly, at the top of spt_process_cell. This is deliberate: letting the absence emerge from an all-empty supports array would make strict geodesic (correctly) forbid everything and return zero tracks for the cell.

Check. That cell's _settings.txt reports tracking.link_mode = euclid, result.have_er = 0, plus the extra line tracking.link_mode_req = geodesic (DOWNGRADED — …). In detection_summary.csv only link_mode = euclid and er_aware = 0 are visible, so use the settings file to tell "I chose Euclidean" from "an ER mode could not run".

What to do. Fix the matching on the Match files tab (the seg files carry a channel token the SPT name lacks; the matcher strips _spt<n>, the ER/mito channel suffixes and your user token, default _VAPB). If a cell genuinely has no ER, do not pool it with ER-linked cells without saying so.

Curate and batch-filter problems

"My _tracks_filtered.xml holds fewer tracks than Tool 1 exported" — an older batch filter wrote over it.

What happened. Before the fix, Tool 2's Run batch filter named its output <base>_tracks_filtered.xml with the name hardcoded, ignoring the export suffix. The viewer reads Tool 1's _tracks_filtered.xml, and the batch Output folder box is pre-filled with that same tracks/ folder — so a batch run with the shipped defaults read Tool 1's tracking output and wrote the twice-filtered result straight back over it. No warning, no backup, and re-running the batch filtered the already-filtered tracks again.

How to tell. Open the XML's first lines and read tracks/<base>_settings.txt beside it. Any one of these is decisive:

  • N_SPOTS="" on the <Track> elements. Tool 1's export writes <Track TRACK_ID="0"> with no N_SPOTS attribute at all; Tool 2 copies that attribute from its input and so writes it back empty. Attribute order says the same thing: Tool 1 writes <Spot FRAME= T= X= Y= Z="0.0" SPOT_ID=…/>, Tool 2 puts SPOT_ID first.
  • nTracks lower than filter.tracks_after in _settings.txt. That key records how many tracks Tool 1's export actually wrote and nothing in Tool 2 updates it, so a smaller nTracks in the file means the file is no longer Tool 1's.
  • TRACK_IDs with gaps. Tool 1's export renumbers the survivors 0…K−1 contiguously; Tool 2 keeps the ids it was given, so a non-contiguous id list inside a _filtered XML is a Tool 2 write. The _spots_filtered.csv next to it still carries the full contiguous set, because the old batch wrote no spots CSV — that mismatch is the same evidence seen from the other side.

What to do — the file itself cannot be repaired. It holds only the tracks that survived the second filter; the ones the batch dropped are simply not in it, and nothing was backed up. Re-run Tool 1 for that cell:

  • If tracks/<base>_spots.csv is still there — the old batch never wrote or touched the raw pair — you do not need to re-detect. Tool 1's Track & filter tab reads that CSV and Export re-writes both _filtered files from it. Put Min track length and Min displacement back to the values recorded as filter.min_track_len and filter.min_disp_um in that cell's _settings.txt and the re-export reproduces the original exactly.
  • If the raw pair is gone too, re-run detection and tracking for the cell (▶ Run) and then Export. Every parameter is in _settings.txt, so the run is reproducible — it is just the full cost.

Then rebuild. Any .mat built while the clobbered XML was in place was built from twice-filtered tracks and is not comparable to a normally curated build, so rebuild it once the pair is restored. Current builds cannot do this: the batch writes _tracks_curated.xml, and every batch write is checked against the file it read and refused if it would land on it.

Build and import problems

build_trackstruct:noXML or TrackImporter_direct:noXML — "No files matching …".

The tracks folder holds no XML matching the pattern being imported. Build & QC picks the pattern for you, preferring *_tracks_curated.xml, then *_tracks_filtered.xml, then *_tracks.xml — so this means the folder has none of the three. Confirm you pointed at <project>/tracks/ and that Tool 1's export actually wrote there (its status line names the folder).

TrackImporter_direct:doubleLag — "A frame registered twice within a track".

Two spots of one track share a frame, so a (start, lag) pair would be ambiguous and the MSD binning is not well defined. This is the legacy importer's data-integrity check, kept. It should not happen with tracks this pipeline produced; if it does, the XML has been hand-edited or merged from two sources. The importer errors rather than producing a quietly wrong MSD.

TrackImporter_direct:paddedSize — "padded layout is ~N MB in memory at P % occupancy".

Every per-localization field in the build is [nF × nT] with nF set by the single longest track, so one outlier track inflates every column of that cell. The warning fires above ~250 MB, or above ~60 MB when occupancy is under 10 %. Nothing is wrong with the numbers; the concern is that hundreds of cells at that size will not fit in RAM. If you see it, expect to work cell-by-cell rather than pooling everything into one build.

"My numbers changed after a rebuild."

They should have, if the old build predates two corrections in the importer. Both move downstream numbers, so an old .mat is not comparable to a new one — rebuild rather than mix them:

  • CSD is now cumsum(dS1), the cumulative sum of the actual step distance in µm. It used to be cumsum(dS1./dT1) — the per-frame speed — which charges a gap-closed step only its per-frame average and is not even in µm unless every dT is 1. On the reference cell, where 86.6 % of tracks contain a 2-frame gap, total path length ran a median 2.0 % low and up to 11.5 % per track. steps = dS1./dT1 is still the per-frame speed on purpose; only CSD is a distance.
  • MSDerror is now MSDstdev ./ sqrt(cntSD) — each track's own pair count at that lag. It used to be divided by the number of tracks with a finite MSD at that lag, so error bars came out a median 4× too small (from 10× too small to 3.7× too large).

MSD itself was independently verified correct and is unchanged, so D and R² from an old build are still sound — it is the path lengths and the error bars that moved.

The wrong build is open, or a downstream tab disagrees with Build & QC.

Every stage resolves the build through one function, cs_active_trackstruct, so they cannot disagree about which file — but they can all be pointing at a file you did not mean. Read analysis/active_trackstruct.txt: it holds one line, the basename in force. If it is missing or names a file that no longer exists, resolution falls back to TrackStruct.mat, then Tracks.mat, then any other .mat in the folder that contains a Tracks variable — which is how a hand-copied build can quietly become active. Fix it by loading the build you want in Build & QC (📂 Load TrackStruct…), which rewrites the pointer. With more than one build present, that button always opens a file picker rather than jumping to the active one.

The Channel dropdown in the picker is greyed out.

That build has no confined/stateChange fields, so there are no diffusion-state channels to select and the dropdown is disabled with Tracked forced. Per-localization diffusion is computed at build; a build made before that existed lacks it. Loading such a build fills the fields in, or rebuild. Note also that switching channel invalidates the per-window density and Monte-Carlo caches — re-run Detect afterwards, or you are looking at sites found on the previous channel.

Contact-site, mapper and dwell problems

cs_window_mapper:noSites — "no CSsites for <cell> — skip".

That cell has no csIDs/<cell>_CSsites.txt, so the mapper skips it and moves on: the run does not fail, it just produces nothing for that cell. Either you never picked sites for it, or you saved with zero sites in every window — in which case the picker deletes the file on purpose, so that a cell you cleared cannot keep stale picks. The mapper also skips a cell whose build has no matrix (cs_window_mapper:noMatrix).

cs_window_mapper:staleFootprint — "skipped a stale refined footprint … (the pick moved — re-run the Refine tab)".

A refined footprint is keyed by file|csID|window, and csID is only a positional site index — so a CS_footprints.mat left over from a previous pick-set would silently map footprints onto the wrong sites. The guard compares the saved pickPx to the current site's pick and applies the override only within 1.5 density px. Seeing this warning means you re-picked sites after refining: re-run the Refine tab so the footprints match the new picks. The same guard protects deletions and the Sites tab's track exclusions.

cs_window_dwell:noCSW — "Run the mapper first".

Dwell reads analysis/CSW_final.mat and nothing else. Run the Sites tab's mapper first. cs_window_dwell:empty means the file exists but contains no sites — every candidate was skipped (deleted in Refine, or no cell had picks).

A site shows a large cloud n but trk = 0, and Dwell reports nothing for it.

Not a bug. Membership and the dwell coordinate frame are always computed on the tracked matrix, because dwell needs track continuity; only the density and enrichment may come from the wider localization cloud. A site built on untracked detections therefore has localizations but no member tracks, and Dwell skips it (it needs CSmatrix and tracks to be non-empty). Read it as what it is: an immobile or blinking structure whose detections never linked into a curated track.

The window ranges or density source are not what I set.

Both are locked to the picker's saved state, on purpose. Density_<cell>_CSwindows.mat is authoritative for window frame ranges — the mapper and Refine never recompute them — and windows.source overrides the mapper's own opts.src, so an old pick keeps the density source it was made with until you re-pick. If that file is missing entirely, downstream silently falls back to one whole-movie window ([-Inf Inf]) per distinct Slice, which will look like your windowing was ignored. Re-save from the picker to restore it.

App and filesystem problems

"MATLAB says a callback errored after I edited an app file."

MATLAB apps do not hot-reload. A figure built from the previous version of the file keeps running the previous code, and a stale figure throws phantom callback errors that do not correspond to anything in the source you are reading. Close the window and relaunch (run_track / run_curate / run_analyze) after every edit. If the error persists after a clean relaunch, it is real.

A provenance file did not appear, and nothing complained.

Several writers are deliberately non-fatal, so that a permission or path problem cannot lose the analysis they are describing. spt_write_settings, spt_append_detection_summary, spt_append_filter_settings, the mapper's metrics CSV and the dwell CSVs all return silently if the file cannot be opened; the picker wraps its provenance JSON and stats CSV in try blocks so a failure there still leaves _CSsites.txt written. The data files (spots CSV, tracks XML) do error out loudly. So: if _settings.txt or detection_summary.csv is missing after a successful run, check that tracks/ is writable — and be aware that Tool 2's Import & Curate then cannot auto-fill its tracking parameters and you must set the three fields by hand.

Tool 1's _tracks_filtered.xml looks over-filtered after a batch run.

See the warning above: Batch filter writes <base>_tracks_filtered.xml into its output folder, which is pre-filled with the same tracks/ folder — so it overwrites Tool 1's filtered XML with the twice-filtered result, and writes no matching spots CSV or _track_metrics.csv. If you need both stages side by side, point the batch box at a separate folder, or step through the cells with Export + Next, which writes the _curated pair instead.

The Experiment tab's counts are blank (–) for a stage that clearly ran.

A dash means the file that would report that number does not exist — the counts are re-derived from the filesystem on every scan, never stored in the manifest. nSpotsRaw/nTracksRaw come from _settings.txt and the XML headers; the kept-vs-total columns come from <base>_track_metrics.csv, which only Export curated writes — so a cell you batch-filtered has no metrics file and shows dashes there. Nothing is wrong with the data; the cheap source for that particular number is absent. (No count is ever obtained by row-counting a 20 MB spots CSV, which is why the cheap sources matter.)

build_trackstruct:looseGlob — "N filtered file(s) matched the raw glob".

A defensive check: on a platform where dir('*_tracks.xml') is loose enough to also match *_tracks_filtered.xml, importing "raw" could pick up filtered files. The importer still keys on _tracks.xml, so the result is intended — but if you see this, confirm which files actually came in from the importer's per-file log lines.

Two folders to leave alone. tool2_analyze/ContactSites_original/ is the pristine Nature-2024 reference implementation — read it, never run or edit it. And do not write into the WithER reference dataset: a stray write there once followed a directory symlink and rewrote WithER/tracks/cs_calib.mat three times. Nothing was lost that time; work in a copy.
